# ライセンス対応の記録と運用ガイド

作成日: 2026-09-27  
対象: Turtle Video のリポジトリ、Web/PWA の配布ビルド、GitHub Pages での公開

## 1. この文書の目的

今回のライセンス表示と第三者 OSS の告知に関する対応を記録し、次のリリースでも同じ手順で確認できるようにする。前半は開発者向けの説明、後半は AI が変更時に参照する作業ルールとする。

AI による定型確認と作業手順は `.agents/skills/app-add-license/SKILL.md` にもまとめる。

**OSS の著作権・ライセンス条件への対応と、第三者の特許を侵害していないかという判断は別の問題である。** この文書と自動生成された告知ファイルは、特許非侵害や全ライセンス条件の充足を証明するものではない。

## 2. 公開者の前提と懸念

- 自分用に作った動画編集アプリを、公開・リリース方法を学びながら、無償の OSS として公開している。現時点で事業化はしていない。
- GPLv3 を想定して公開してきた。ライセンス条件と利用 OSS の一覧は既に明記しており、ソフトウェアの提供形態を一定程度整えていると理解している。
- 個人で全世界の関連特許を網羅的に調べることはできない。無償・非事業であることを踏まえ、現実的な確認と、具体的な指摘があった場合の速やかな対応を重視したい。
- 「指摘されたら機能を改善・変更する」という方針。ただし、指摘の内容と権利の範囲を確認してから、修正・一時停止・専門家相談などを選ぶ。単に機能を変更するだけで過去分を含む問題が自動的に解消するとは扱わない。

これらは公開者の状況と運用方針の記録であり、無償公開なら特許や著作権の問題が生じないという意味ではない。

## 3. 今回の対応前にできていたこと・不足していたこと

| 項目 | 対応前の状態 | 今回の判断・対応 |
| --- | --- | --- |
| プロジェクト自身のライセンス | ルート `LICENSE` に GPLv3 本文と「version 3 or any later version」の告知があり、ソースヘッダーも `GPL-3.0-or-later` だった | この選択を維持し、他の表記を統一した |
| README と OSS の一覧 | ライセンス条件と直接・間接依存のライセンス名を案内していた | 一覧は引き続き維持。ただし、名前の一覧は各パッケージの告知原文の代わりにはならない |
| バージョン表記 | `package.json` と `package-lock.json` のルートは `GPL-3.0` で、`LICENSE` 等と不一致だった | 両方を `GPL-3.0-or-later` に統一した |
| 特許についての説明 | README の記述は GPLv3 による保護を広く受け取れる余地があった | GPLv3 の貢献者による特許ライセンスの規定と、第三者特許の非侵害保証は別であることを明記した |
| 間接依存の件数 | アプリ内ヘルプの集計値が `package-lock.json` と一致しなかった | ルートを除く `packages` の 677 エントリを再集計した。これは **配布物に含まれるパッケージ数ではない** |
| 配布ビルドの第三者告知 | 実行時にバンドルされる第三者 OSS の著作権表示・許諾文をまとめたファイルが `dist/` に無かった | ビルド後に告知ファイルを生成し、アプリ内ヘルプからも開けるようにした |

## 4. 今回実装した内容

### 4.1 GPL の表記と説明

プロジェクトの選択は **GPLv3 またはそれ以降のバージョン**、SPDX 識別子は `GPL-3.0-or-later` とする。これは GPLv3 を含み、利用者に将来の GPL バージョンを選ぶ余地を認める。今回、新しく `-or-later` に切り替えたのではなく、既存の `LICENSE` とソースヘッダーの選択に `package.json`、`package-lock.json`、README、ヘルプの説明を合わせた。`GPL-3.0-only` へ変える場合は公開者の明示的な方針変更として扱い、既存の告知や他者の寄与も確認する。

README とアプリ内ヘルプには、外部へ改変版を配布する場合の GPL 条件を説明した。GPL の詳細な義務は配布形態や改変内容に依存するため、短い説明を条文の代用にしない。正本はルートの `LICENSE` とする。

### 4.2 依存ライセンスの表示

`src/constants/sectionHelp.ts` にある一覧は、`package.json` の直接依存・開発依存と、`package-lock.json` 全体のライセンス集計を説明するもの。全 677 件はロックファイルのエントリ数であり、同名パッケージの別階層を個別に数えている。これを「実際の配布物の OSS 677 件」と説明してはいけない。

### 4.3 配布ビルドの告知ファイル

`npm run build` は `tsc`、Vite ビルドに続けて `scripts/generate-third-party-licenses.mjs` を実行する。スクリプトは `dist/` のソースマップから第三者パッケージを検出し、ソースマップに帰属が出ない生成コード・CSS に関係する `vite`、`vite-plugin-pwa`、`tailwindcss` も明示的に含める。各パッケージの `LICENSE` / `LICENCE` / `COPYING` / `NOTICE` 系ファイルの原文を集め、次の二つを `dist/` に作る。

- `LICENSE.txt`: ルート `LICENSE` のコピー。プロジェクト自身の GPL 告知と条文。
- `THIRD_PARTY_LICENSES.txt`: 検出した第三者パッケージの名前・バージョン・宣言ライセンス・告知ファイル原文。

告知ファイルやライセンス情報が見つからない場合、スクリプトはビルドを失敗させる。2026-09-27 の検証ビルドでは、第三者 **17 パッケージ**分を生成した。この数は依存更新やビルド内容で変わる。`dist/` は生成物であり、GitHub Pages のワークフローは `npm ci` → `npm run build` → `dist/` をアップロードする。アプリ内ヘルプの「ライセンス」から両ファイルにリンクする。

当初提示された `license-checker-rseidelsohn --files ... --out ...` の例では、`--files` は個別ファイルのコピー、`--out` はレポート出力であり、それだけで単一の全文告知ファイルが完成するわけではない。また `--production` だけでは PWA の生成コードなどを見落とし得る。今回の方式も自動検出の範囲に限界があるため、ツール導入やファイル生成をもって「完全にクリア」とは判定しない。

## 5. 残る確認範囲と今後必要なこと

### 通常の依存更新・リリース時

1. `package.json` / `package-lock.json` の変更を確認し、新規・更新パッケージの原文ライセンスと GPL との組み合わせ、追加条件、例外、同梱 `NOTICE` を確認する。ライセンス名だけで判断しない。
2. `npm run build` を実行し、`dist/LICENSE.txt` と `dist/THIRD_PARTY_LICENSES.txt` が生成され、後者に対象パッケージの著作権表示・許諾文が入っているか確認する。件数の増減があれば理由を調べる。
3. ソースマップに現れない生成コード、PWA のサービスワーカー、CSS、手動コピーしたコード、画像・フォント・音声・動画などの静的素材、CDN から取得する素材を個別に点検する。必要な場合は生成対象または別の告知・配布方法を追加する。
4. アプリ内ヘルプの直接依存一覧とロックファイル集計を更新し、配布物の件数と混同する文言がないか確認する。
5. 配布形態ごとに、GPL 本文・対応するソースコードへの提供方法・第三者告知への到達方法を確認する。GitHub Pages 以外の ZIP、インストーラー、ミラー、オフライン配布を追加したら、それぞれの成果物で再確認する。
6. 公開後は実際の公開 URL で両ファイルとヘルプのリンクを開いて確認する。ローカルビルドの成功だけではデプロイ結果は確定しない。

自動生成は `dist/**/*.map` と明示リストを起点にしており、`vite.config.ts` のソースマップ出力が前提となる。パッケージ外の素材や新しい生成方式は網羅しない。現状、両告知ファイルが PWA のオフライン用キャッシュに含まれるかは検証していない。ライセンスの互換性、個別の追加義務、第三者の特許も自動判定していない。依存の大幅更新、新規素材の追加、配布形態の変更、事業化の検討時には、必要に応じて専門家へ確認する。

### 特許などの具体的な指摘を受けた場合

1. 指摘文、受領日、相手、対象の国・権利番号・請求項・問題とされる機能、対象バージョンを保存する。公開中の実装と変更履歴も記録する。
2. 実際の権利の有効性・地域・請求項とアプリの実装の対応を確認する。事実が不明なまま「侵害している」「変更すれば解決する」と断定しない。
3. 具体性と影響が高ければ、当該機能の一時停止、設計変更、公開範囲の見直しなどを検討し、弁理士・弁護士や知財相談窓口に相談する。回答期限がある場合は優先して扱う。
4. 対応内容と判断理由を記録し、必要な説明を更新する。ライセンス表示を増やすだけでは特許の指摘への回答にならない。

## 6. 今後 AI がライセンス関連の作業を行う際のルール

この節は依存追加・更新、素材追加、README やヘルプのライセンス表記変更、ビルド・PWA・デプロイ変更、リリース準備、ライセンスや特許に関する問い合わせ対応に適用する。

1. **現物を先に読む。** `LICENSE`、`package.json`、`package-lock.json`、README のライセンス節、`src/constants/sectionHelp.ts`、`scripts/generate-third-party-licenses.mjs`、`vite.config.ts`、配布ワークフロー、およびこの文書を確認する。記録された 677 件・17 件は固定値として扱わない。
2. **三つの対象を分ける。** プロジェクト自身の GPL、依存関係の表示・集計、実際の配布物の第三者告知を混同しない。特許の論点はさらに別に扱う。
3. **変更の影響を追う。** 新しいコード・パッケージ・素材が最終的にどの成果物へ入るかを確認する。ソースマップで検出できないものは明示リストや個別告知を検討し、必要な原文と著作権表示を保持する。ライセンス名だけを告知完了の根拠にしない。
4. **表記の整合性を保つ。** プロジェクトの現行選択は `GPL-3.0-or-later`。変更が必要な場合は権利関係と公開者の意図を確かめ、`LICENSE`・メタデータ・README・ヘルプ・ソースヘッダーを一体で見直す。
5. **再生成して成果物を検査する。** `npm run build` の成否、二つの告知ファイルの存在と内容、アプリ内リンク、必要なら公開先での到達性を確認する。依存が変わったらヘルプの一覧・集計も再計算する。
6. **結論の範囲を明示する。** 「今回確認した範囲」「未確認の素材・配布形態」「特許非侵害は未判断」を分けて報告する。自動生成だけを理由に完全準拠・特許非侵害を宣言しない。
7. **具体的な権利の指摘は個別に扱う。** 事実を保存して請求項や実装を照合し、影響に応じて公開停止・修正・専門家相談を提案する。相手への連絡や法的な認否は公開者の判断を要する。
