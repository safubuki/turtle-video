# セクションヘルプシステム 設計仕様書

## 1. 概要と背景

アプリケーションの高機能化・多機能化に伴い、ヘルプの内容が膨大になり「読みにくい」「目的の設定が見つからない」という課題が生じた。
これに対し、従来の「長文マニュアル型ヘルプ」や「アイコンの末尾羅列」を廃止し、**実際の操作動線・画面構成と完全に一致した階層型インラインヘルプシステム**へと刷新した。

本仕様書は、Turtle Video におけるセクションヘルプの実装特徴、UI/UX設計原則、技術仕様を体系化し、他アプリケーションでヘルプを新設・刷新する際の標準リファレンスとして機能することを目的とする。

---

## 2. 課題と解決アプローチ

| 従来の課題 | 解決アプローチ |
| :--- | :--- |
| **説明文が長大でスクロールが大変** | カテゴリ単位で折りたためるアコーディオン構造を導入。閉じた状態では「目次」として機能し、一目で目的の設定へ到達可能にした。 |
| **アイコン・ボタンが下にまとめて固めて表示され、説明と対応しない** | 各箇条書き項目の直下に該当する操作パーツをインライン配置（`bullet.visuals`）。説明と実物が1対1で直結して理解できるようにした。 |
| **説明のない孤立したアイコン見本が存在** | 意味が伝わらない孤立見本は、説明文側に対応解説を追加するか、文字説明だけで十分なものは省略した。 |
| **アコーディオンの中にさらにアコーディオン見本が表示されるメタ混乱** | 「ロゴ表示 >」「キャプション一括設定 >」などの入口ヘッダー枠の見本を完全排除し、中の操作部品（タブ、ボタン、スライダー）だけを表示。 |
| **カードの領域境界がわかりにくい** | 暗い背景と同化しないようカード枠線を `border-2 border-gray-600/80` に強化し、どこからどこまでが1つの設定かが直感的に分かるようにした。 |
| **PCとモバイルでの操作表記の違和感** | PC表示では「クリックで開閉」、スマホ表示では「タップで開閉」とレスポンシブにテキストを自動切り替え。 |

## 3. UI / UX 設計原則

### 3.1. 操作体験と一致する階層構造
ヘルプの表示順序は、ユーザーが画面を操作する自然な順序（メンタルモデル）と一致させる。

```
[親アコーディオン: カテゴリ] （例: 動画・画像カテゴリ）
  ├── 1. 基本アクション（直接表示・アコーディオン無し）
  │      └── 追加ボタン、アスペクト比切替など
  ├── 2. カテゴリ全体設定（親アコーディオン）
  │      └── タイトル、ロゴ表示、音声一括設定など
  └── 3. 個別カード設定（親アコーディオン）
         ├── 直接表示: 上下移動、複製、削除、トリミング
         └── 子アコーディオン: 各詳細調整（位置・サイズ、速度、フェード等）
```

- **目次としての活用**: 初期状態では主要カテゴリが閉じており、全体の目次として俯瞰できる。「すべて開く」「すべて閉じる」ボタンも常設。
- **浅い階層の維持**: 無制限に入れ子にせず、最大でも「カテゴリ」→「カード設定」→「詳細調整」の2段階に抑える。

### 3.2. 操作見本（ビジュアルトークン）のインライン配置原則
- **直下配置**: 説明文の直下に、該当するボタン・アイコン・入力見本をインデントして配置する。
- **重複描画の防止**: 箇条書き内で使用されたビジュアルIDは Set で管理し、カード末尾の全体見本エリアから自動除外する。
- **実画面への完全な忠実性**: 実画面のコンポーネント（ボタンの配色、ラベル、アイコン、並び順）と完全に同一の外観でレンダリングする。

### 3.3. 入口アコーディオンヘッダー見本の排除原則
ヘルプ項目がすでにアコーディオンで開閉されている状況で、さらにその中に「〇〇設定 ＞」というアコーディオン見出しの見本を表示すると、ユーザーは「ヘルプを操作しているのか、見本なのか」「もう一度押せるのか」と混乱する。
したがって、**アコーディオン開閉ヘッダー枠自体の見本は一切表示せず、展開後の実操作ボタン・コントロールのみを見本とする**。

### 3.4. 境界線（Border）とコントラスト設計
ダークテーマにおいて、背景色（例: `gray-900`）に対してカード枠線が薄いと（例: `gray-700/60`）、カードの領域の開始・終了が判別できなくなる。
- **太さ**: `border` (1px) ではなく、カード枠には **`border-2` (2px)** を採用する。
- **カラー**: `border-gray-600/80`（開いた時は `border-gray-500/90` + ほのかなシャドウ）。
- **注意点**: 3px以上（border-4など）にすると厚ぼったくなりモダンな洗練さを損なうため、2px が視認性とデザイン性の最適な黄金比である。
- **CSS変数・カラー定義の整合性**: Tailwind 等で未定義のカラー（例: `gray-750`）を指定すると、CSS仕様により `currentColor`（親の白文字色）へフォールバックして不自然な白線になる事故を防ぐため、必ず定義済みカラーを使用する。

## 4. アーキテクチャとデータ構造

ヘルプシステムは **データ定義（`sectionHelp.ts`）** と **UIレンダラー（`SectionHelpModal.tsx`）** を完全に分離している。

### 4.1. データモデル (`src/constants/sectionHelp.ts`)

```typescript
export type SectionHelpKey = 'app' | 'clips' | 'bgm' | 'narration' | 'caption' | 'preview';

export interface SectionHelpBullet {
  text: string;
  visuals?: SectionHelpVisualId[]; // 説明行に直結する操作見本ID
}

export interface SectionHelpItem {
  title: string;
  category?: string;              // 所属カテゴリ（アコーディオン分類用）
  isSubAccordion?: boolean;        // カテゴリ内の子アコーディオンにするか
  description: string;            // 概要（140文字以内）
  bullets?: Array<string | SectionHelpBullet>; // 箇条書き（インライン見本対応）
  facts?: Array<{ label: string; description: string }>; // 定義・要点一覧
  comparison?: {                  // モード比較表
    caption: string;
    rows: Array<{ label: string; description: string }>;
  };
  note?: string;                  // 注意事項・ポイント
  visuals?: SectionHelpVisualId[];// 全体見本（bulletsで未消化のもののみ末尾表示）
}

export interface SectionHelpDefinition {
  title: string;
  subtitle: string;
  items: SectionHelpItem[];
}
```

### 4.2. プラットフォーム / Flavor による動的適応
- **Flavor フィルタリング**: iPhone/iPad Safari（`apple-safari`）向けには、非対応機能（WebCodecs依存機能や一部高度編集）のヘルプ項目を自動除外する。
- **動的文言切り替え**: 保存先ダイアログ（File System Access API）の対応可否に応じて、ダウンロード手順の説明文を動的に切り替える（`getDownloadHelpSentence`）。

## 5. テスト戦略と保守性

ヘルプの品質と正確性を恒久的に保証するため、Vitest による自動テストを完備している。

1. **仕様・文言の自動チェック (`src/test/sectionHelp.test.ts`)**:
   - 導入文が140文字以内に収まっているか（冗長な説明の排除）
   - Flavor 境界で非表示にすべき機能が確実にフィルタリングされているか
   - 重要な操作キー・数値（「0.1秒単位」「実尺」など）が漏れなく含まれているか
   - 登録されたすべての `visuals` が有効なトークンIDであるか
2. **UIレンダリングの検証 (`src/test/sectionHelpModal.test.tsx`)**:
   - 初期状態（閉じた状態）から開いた状態への遷移が正常か
   - アコーディオンの開閉・全展開で React Hooks エラーが発生しないか
   - 実画面と一致する見本コンポーネント（スロット、文字揃え、ボタン等）がDOMに正しく出力されるか

## 6. 今後の開発・他アプリ展開への教訓

1. **「見ればわかるUI」と「ヘルプ」を同一言語にする**:
   ヘルプ内の文言と実際の画面上のラベルが 1 文字でも異なると、ユーザーは迷う。ヘルプ上の文言・アイコン・ボタン見本は実画面と完全一致させる。
2. **メタな枠線・見出し見本を作らない**:
   「開くためのアコーディオンボタン」をヘルプ見本の中に入れてはならない。見せるべきは「設定そのもの」である。
3. **未定義CSSクラスのフォールバック事故に留意**:
   コンポーネント作成時は、Tailwind 設定にない中間色（例: `gray-750`）を使って `currentColor` にフォールバックするミスを防ぎ、設計されたパレットのみを使用する。
