# エビデンス台帳

このスキルが主張する UI/UX 原則の**出典・確度・適用限界**を記録する。目的は2つ：

1. 提案の根拠をユーザーに提示できるようにする
2. **よく信じられているが実は不正確な主張**を、このスキル自身が再生産しないようにする

> 📌 使い方: UI 提案でここに載っている原則を引くときは、確度と限界も一緒に伝える。「ベストプラクティスだから」で押し切らない。

---

## 確度の区分

| 区分 | 意味 |
|------|------|
| **規範** | 公的標準。準拠が要求されうる（WCAG 2.2 など） |
| **草案** | 標準化の途上。将来変わりうる。準拠の根拠にはできない |
| **実証** | 査読研究またはユーザー調査に裏付けられた知見 |
| **経験則** | 実務で広く支持されるが定量的裏付けは限定的 |
| **要注意** | 広く流布しているが、誤用・誇張・陳腐化がある |

---

## A. アクセシビリティ

| 主張 | 確度 | 出典 | 適用限界 |
|------|------|------|---------|
| 本文コントラスト 4.5:1、大テキスト 3:1 | **規範** | WCAG 2.2 SC 1.4.3 (AA) | 輝度比のみで極性・字幅を考慮しない。「通ったが読みにくい」は起こる |
| UI部品・グラフィックは 3:1 | **規範** | WCAG 2.2 SC 1.4.11 | 装飾目的の要素は対象外 |
| タッチターゲット最小 24×24 CSS px | **規範** | WCAG 2.2 SC 2.5.8 (AA) | 44px は Apple HIG 由来の**快適性**目標であり WCAG AA の要求値ではない |
| `prefers-reduced-motion` を尊重する | **規範** | WCAG 2.2 SC 2.3.3 / OS設定 | AAA基準だが、前庭障害への影響が大きいため実務上は必須扱い |
| 色のみで情報を伝えない | **規範** | WCAG 2.2 SC 1.4.1 (A) | — |
| スキップリンクの提供 | **規範** | WCAG 2.2 SC 2.4.1 (A) | — |
| フォーカスの可視化 | **規範** | WCAG 2.2 SC 2.4.7 / 2.4.11 | `outline: none` 単独は違反。代替リングがあれば可 |

### ⚠️ 要注意: 「APCA が WCAG 3 の新基準」

**この主張は誤り。** 2026年時点で WCAG 3.0 は Working Draft のままで、ドラフト自身がコントラスト算法を "yet to be determined" としている。APCA は最有力候補で Chrome DevTools に実験的搭載もされているが、**確定していない**。

**正しい運用**: WCAG 2.2 = 準拠の床、APCA = 可読性の天井、という二層構造で扱う。準拠を語る文脈で APCA を根拠にしない。

### ⚠️ 要注意: 「タッチターゲットは 44px が必須」

44×44pt は Apple Human Interface Guidelines の推奨値で、**WCAG の要求ではない**。WCAG 2.2 SC 2.5.8 (AA) の要求は 24×24 CSS px。Material Design は 48dp を推奨する。「44px 未満は違反」と断言すると誤り。**24px が下限、44px 以上が望ましい**が正確な言い方。

## B. パフォーマンス

| 主張 | 確度 | 出典 | 適用限界 |
|------|------|------|---------|
| LCP < 2.5秒 | **規範**（業界標準） | Google Core Web Vitals | 75パーセンタイルでの評価 |
| INP < 200ms | **規範**（業界標準） | Core Web Vitals | 同上 |
| CLS < 0.1 | **規範**（業界標準） | Core Web Vitals | 同上 |
| `transform`/`opacity` のみアニメートすると 60fps を保ちやすい | **実証** | ブラウザレンダリングパイプラインの構造 | 合成レイヤーが過剰だとメモリを圧迫する。`will-change` の乱用は逆効果 |
| 応答が 100ms 以内なら「即座」と感じる | **実証** | Card, Robertson & Newell (1991) / Nielsen (1993) | 個人差・タスク文脈で変動する |

### ⚠️ 要注意: 「FID（First Input Delay）」は廃止済み

**FID は 2024年3月12日に INP（Interaction to Next Paint）へ置き換えられた。** FID を Core Web Vitals として挙げるのは陳腐化した情報。

FID が置き換えられた理由：最初の1回の入力遅延しか測らないため、初回が速ければ以降が遅くても合格してしまう。INP は全インタラクションを評価し、入力からペイント完了までの全体を測る。**閾値は 200ms 以下が良好、500ms 超が不良。**

### ⚠️ 要注意: Doherty 閾値（400ms）

「400ms 以内の応答で生産性が上がる」という主張の出典は 1982年の IBM メインフレーム端末の研究。**現代の Web UI に直接適用できる数値ではない。** 「速いほど良い」という方向性は妥当だが、400ms という具体値を根拠として提示するのは避ける。Core Web Vitals の INP を使うほうが正確。

## C. ナビゲーションとスクロール

| 主張 | 確度 | 出典 | 適用限界 |
|------|------|------|---------|
| 閲覧時間の約74%が最初の2画面分に集中 | **実証** | NN/g スクロール調査 | ページ種別で変動。長文記事では下部滞在が増える |
| スクロールジャッキングは有害 | **実証** | NN/g "Scrolljacking 101" | ブラウザ標準のスクロール量を奪う実装が対象。`scroll-behavior: smooth` は該当しない |
| 常時スティッキーヘッダーは可読領域を奪う | **実証** | NN/g "Sticky Headers" | 回遊が主タスクのページでは利点が上回る。**記事系では妨害になりやすい** |
| 段階的開示は学習容易性を高めエラーを減らす | **実証** | NN/g "Progressive Disclosure" | 必須情報を隠すと発見性が落ちる。低頻度機能にのみ適用 |

### ⚠️ 要注意: 「スムーズスクロールは常に良い」

**無条件では正しくない。** 前庭障害を持つユーザーには大きな画面移動が体調不良を引き起こす。`@media (prefers-reduced-motion: no-preference)` でのガードが**必須**。

またスムーズスクロールには副作用がある：
- 長距離ジャンプでは移動完了までの待ち時間が発生し、かえって遅く感じる
- スクロール中に再度クリックされたときの挙動が壊れやすい

**「ヌルッと動く」の実現手段はブラウザネイティブの `scroll-behavior: smooth` で十分。** ホイール量を奪う独自実装（スクロールジャッキング）で作らない。

## D. 情報設計・認知

| 主張 | 確度 | 出典 | 適用限界 |
|------|------|------|---------|
| Hick の法則（選択肢が増えると決定時間が対数的に増加） | **実証** | Hick (1952), Hyman (1953) | 等質な選択肢からの単純選択が前提。視覚的階層があれば負荷は下がる |
| Fitts の法則（距離とサイズで到達時間が決まる） | **実証** | Fitts (1954) | ポインティング動作の予測モデル。タッチでも概ね成立 |
| 逆ピラミッド構成が Web に適する | **経験則** | ジャーナリズム由来 + スキャン行動調査 | — |
| 60-30-10 の配色比 | **経験則** | インテリアデザイン由来 | 科学的検証はない。破綻しにくい配分の目安 |
| F パターンの視線移動 | **実証** | NN/g アイトラッキング | **「目指すべき型」ではなく階層設計が弱いときの兆候** |

### ⚠️ 要注意: 「Miller の法則（7±2）」の UI への適用

Miller (1956) の研究対象は**短期記憶に保持すべき無関係な項目数**であり、**画面に表示され続けている項目**には当てはまらない。「ナビは7項目まで」の根拠として Miller を引くのは誤用として広く指摘されている。

ナビ項目を絞る妥当な根拠は Hick の法則とスキャン効率のほうにある。

### ⚠️ 要注意: 「3クリックルール」

「どのページも3クリック以内で到達すべき」という主張は、**ユーザー調査で否定されている**。クリック数と離脱率に有意な相関は見つかっておらず、重要なのは**各クリックで正しい方向に進んでいる確信が持てるか**。クリック数を減らすために1画面に選択肢を詰め込むのは逆効果。

## E. 「Wow Factor」の扱い

| 主張 | 確度 | 注意 |
|------|------|------|
| 感情的デザインの3層（本能的/行動的/内省的） | **経験則** | Norman "Emotional Design" (2004) の枠組み。有用なレンズだが測定可能な基準ではない |
| マイクロインタラクションが満足度を高める | **経験則** | 過剰だと遅さと煩わしさに転じる |

**このスキルの立場**: Wow Factor は**アクセシビリティとパフォーマンスを削って得るものではない**。両立しない場合は、規範（WCAG）と実測値（Core Web Vitals）を優先する。演出のための演出は削る。

## F. 台帳の更新

以下のときにこの台帳を更新する：

- WCAG 3.0 のコントラスト算法が確定したとき（APCA の位置づけが「草案」から変わる）
- Core Web Vitals の指標・閾値が変更されたとき
- スキル内の主張に対して、反証となる調査結果が出たとき
- ユーザーから「その根拠は？」と問われて即答できなかったとき

> 出典を確認せずに数値を書き足さない。記憶した数値は陳腐化する（FID の例）。不確かなときは確度欄に「要確認」と書いて残す。
