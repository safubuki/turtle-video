# 配色の科学的根拠

「なんとなく綺麗」ではなく、測定可能な根拠で配色を決めるためのリファレンス。数値検証は `scripts/ux_audit.py contrast` / `palette` で行う。

---

## 1. コントラスト: 何を基準にするか

### 二層構造で考える

| 層 | 基準 | 位置づけ |
|----|------|---------|
| **法的・準拠の床** | WCAG 2.2（4.5:1 / 3:1） | **現行の唯一の規範**。監査・調達・訴訟で参照されるのはこれ |
| **可読性の天井** | APCA Lc | **参考値**。WCAG 3 は Working Draft で、コントラスト算法は未確定 |

> ⚠️ **よくある誤解**: 「APCA が WCAG 3 の新基準に決まった」は**誤り**。2026年時点で WCAG 3.0 は Working Draft のままであり、ドラフト自身が contrast algorithm を "yet to be determined" としている。APCA は最有力候補だが確定ではない。**準拠を語る場面では WCAG 2.2 を使う。**

### WCAG 2.2 の閾値（現行規範）

| 対象 | AA | AAA |
|------|-----|-----|
| 通常テキスト（< 18.66px bold / < 24px） | 4.5:1 | 7:1 |
| 大きなテキスト（≥ 18.66px bold または ≥ 24px） | 3:1 | 4.5:1 |
| UI部品・グラフィック（境界線、アイコン、フォーカスリング） | 3:1 | — |

### WCAG 2.x 相対輝度式の限界（なぜ APCA が生まれたか）

WCAG 2.x の比は単純な輝度比であり、以下を考慮しない：

- **極性**: 黒地に白文字と白地に黒文字を同じ値として扱うが、実際の知覚は異なる（明所視では白地黒文字が読みやすい）
- **フォントの太さ・サイズ**: 同じ色でも hairline の細字と太字では可読性がまったく違う
- **暗色域の非線形性**: 濃い色同士の比を過大評価し、明るい灰色同士を過小評価する傾向

このため「4.5:1 を通ったのに読みにくい」「3.9:1 だが実際は十分読める」というズレが生じる。APCA は極性とフォントサイズを織り込んだ知覚モデルで、この歪みを補正する。

### APCA Lc の目安（参考値）

| Lc（絶対値） | 用途 |
|-------------|------|
| 90+ | 最高水準の本文可読性 |
| 75 | **本文テキストの推奨下限** |
| 60 | 大きめの文字・サブヘッド |
| 45 | UI部品・アイコンなど非テキスト |
| 30 | 無効状態など「見えるが読ませない」要素 |
| 15未満 | 実質不可視 |

Lc の符号は極性を示す。正 = 明るい背景に暗い文字、負 = 暗い背景に明るい文字。

### 実務での運用

```bash
# 単一ペアを両方の基準で同時に検証
python scripts/ux_audit.py contrast --fg "#64748b" --bg "#ffffff"

# パレット全体を総当たりで検証（デザイントークン確定時に必ず実行）
python scripts/ux_audit.py palette \
  --surfaces "#ffffff,#f8fafc,#0f172a" \
  --foregrounds "#0f172a,#475569,#94a3b8,#f1f5f9"
```

**WCAG 2.2 を満たしたうえで、APCA Lc も確認する。** 両方通れば安全、WCAG だけ通って APCA が低い場合は「準拠はしているが読みにくい」サインなのでフォントサイズか太さで補う。

## 2. OKLCH — 知覚的に均等な色空間

### なぜ HSL ではダメか

HSL は「同じ Lightness なら同じ明るさに見える」という前提が**成り立たない**。`hsl(60, 100%, 50%)`（黄）と `hsl(240, 100%, 50%)`（青）は L が同じでも、黄のほうが圧倒的に明るく見える。このため HSL で機械的にパレットを作ると、色相ごとに明度がバラつき、統一感が壊れる。

### OKLCH の利点

`oklch(L C H)` は人間の知覚に沿って設計された色空間で、**L を固定すれば色相が変わっても明るさが揃う**。CSS Color 4 として全モダンブラウザでサポート済み。

```css
:root {
  /* L を揃えると、色相が違っても「同じ強さ」に見える */
  --brand:   oklch(0.55 0.18 264);  /* 青 */
  --success: oklch(0.55 0.18 150);  /* 緑 */
  --danger:  oklch(0.55 0.18  25);  /* 赤 */
}
```

### スケール生成の指針

L を等間隔に動かしてトーンスケールを作る。C（彩度）は両端で落とすと自然になる。

```css
:root {
  --blue-50:  oklch(0.97 0.02 264);
  --blue-100: oklch(0.93 0.05 264);
  --blue-300: oklch(0.78 0.12 264);
  --blue-500: oklch(0.62 0.18 264);  /* 基準色 */
  --blue-700: oklch(0.48 0.16 264);
  --blue-900: oklch(0.33 0.10 264);
}
```

> 生成後は必ず `ux_audit.py palette` でコントラストを検証する。OKLCH は知覚的均等性を与えるが、**WCAG 準拠を保証はしない**。

## 3. 配色比率 60-30-10

インテリアデザイン由来の経験則で、UI でも破綻しにくい配分として広く使われる。**科学的に検証された法則ではなく、視覚的バランスのヒューリスティック**である点は正直に扱う。

| 比率 | 役割 | UI での対応 |
|------|------|------------|
| 60% | 支配色 | 背景・サーフェス（ほぼ無彩色） |
| 30% | 補助色 | カード、境界、セカンダリ領域 |
| 10% | アクセント | CTA、アクティブ状態、重要通知 |

**実務上の含意**: アクセントカラーは画面の 10% 程度に抑える。プライマリボタンを1画面に何個も置くと、10%枠を食い合って「どれが主要アクションか」が消える。

## 4. 色覚多様性への対応

### 前提

男性の約 8%、女性の約 0.5% が何らかの色覚特性を持つ（主に赤緑系の 1型・2型）。**赤と緑の対比だけで情報を伝えると、この層に情報が届かない。**

### 設計ルール

| 問題 | 対策 |
|------|------|
| 成功=緑 / エラー=赤 のみ | アイコン（✓ / ✕）とテキストラベルを併用する |
| グラフの系列を色だけで区別 | 線種・マーカー形状・直接ラベルを併用する |
| 必須項目を赤文字だけで示す | `*` 記号 + `aria-required` を併用する |
| 現在地をハイライト色のみで示す | 太字・下線・左ボーダーを併用する |

**原則（WCAG 2.2 SC 1.4.1 Use of Color, A）**: 色は情報を伝える**唯一の手段であってはならない**。色は常に「二重符号化」の一方として使う。

### 検証方法

グレースケール変換して情報が読み取れるかを見るのが最速の確認。区別がつかなくなる箇所は、色以外の手がかりが欠けている。

## 5. ダークモードの配色原則

| 原則 | 理由 |
|------|------|
| 純黒（`#000`）を背景にしない | 白文字とのコントラストが強すぎ、ハレーション（滲み）と眼精疲労を起こす。`#0f172a` 前後を使う |
| 純白（`#fff`）の本文を避ける | 同上。`#e2e8f0` 程度に落とすと長文が読みやすい |
| 彩度を下げる | 暗背景では同じ彩度でも色が浮いて見える。明所より 10–20% 落とす |
| 明度でエレベーションを表す | 暗背景ではドロップシャドウがほぼ見えない。上のレイヤーほど背景を明るくする |
| アクセント色は明るめに振る | 暗背景では暗いアクセントが沈む。ライトモードより L を上げる |

**重要**: ライトモードで検証したコントラストは**ダークモードでは通用しない**。両モードそれぞれで `palette` を実行する。

```bash
# ライト
python scripts/ux_audit.py palette --surfaces "#ffffff,#f8fafc" --foregrounds "#0f172a,#475569"
# ダーク
python scripts/ux_audit.py palette --surfaces "#0f172a,#1e293b" --foregrounds "#e2e8f0,#94a3b8"
```

## 6. やってはいけない配色

- 🚫 彩度の高い色同士を隣接させる（ハレーション・視覚振動を起こす。例: 純赤の上に純青の文字）
- 🚫 大面積に高彩度色を敷く（目が疲れ、コンテンツが読めない）
- 🚫 プレースホルダーを薄すぎる灰色にする（`#ccc` on `#fff` は 1.6:1 で完全に不適合）
- 🚫 無効状態を「薄くする」だけで表す（理由が伝わらない。ツールチップで説明を添える）
- 🚫 ブランドカラーをそのまま文字色に使う（多くのブランド色は本文コントラストを満たさない。文字用に暗いバリアントを作る）
