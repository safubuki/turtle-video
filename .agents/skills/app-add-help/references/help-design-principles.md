# ヘルプシステム設計・実装原則ガイド

アプリケーションにヘルプ機能を追加する際に遵守すべき UI/UX 原則、構造設計、および実装上の注意点です。

---

## 1. アプリ機能の把握とヘルプへの構造化

### 1.1. ソースコードからの機能抽出アプローチ
ヘルプを作成する際は、実装者の思い込みではなく、**画面上の実際の操作要素**を起点に機能を把握します。
1. **セクション / 画面単位の分類**: ページや主要カード、タブごとにセクションを分割する。
2. **アクションの抽出**: `button`, `aria-label`, アイコン, 入力フィールド（スライダー、セレクト、数値ステッパー）を収集する。
3. **動線の粒度設定**:
   - **第1層（主要カテゴリ）**: 最もよく使う基本操作（例: 素材の追加、形式選択）。
   - **第2層（カテゴリ全体設定）**: プロジェクト全体や一括適用される設定（例: 音声一括、タイトル）。
   - **第3層（個別カード詳細調整）**: 各カードや詳細パネル内の詳細パラメータ（例: 位置・サイズ、フェード）。

## 2. UI / UX 設計の7大原則

### 原則 1: 操作体験と一致する階層構造（アコーディオンの適切な活用）
- **目次としての親アコーディオン**: ヘルプを開いた直後は、各セクションの親カテゴリが閉じた状態（または1つ目のみ展開）とし、全体の目次として機能させる。
- **直接表示と子アコーディオンの使い分け**:
  - 主要な操作（追加、並び替え、削除等）はアコーディオンなしで直接表示する。
  - パラメータが多い微調整（回転、ぼかし、フェード時間等）のみ子アコーディオンに格納する。
- **一括開閉**: 「すべて開く」「すべて閉じる」ボタンを常設する。

### 原則 2: 操作見本（ボタン・アイコン）のインライン直結配置
- **末尾まとめ表示の禁止**: アイコンやボタンをカードの最下部にまとめて羅列してはならない。ユーザーは「どの説明に対応するボタンか」が分からなくなる。
- **箇条書き直下への配置**: 各箇条書き項目の直下に、対応する操作部品をインデントしてインライン配置する。
- **重複描画の排除**: 箇条書き内で使用したビジュアルIDは Set で管理し、末尾の全体見本エリアで二重に表示されないようにする。

### 原則 3: 入口アコーディオンヘッダー見本の排除
- アコーディオンで開閉されるヘルプの中で、さらに「〇〇設定 ＞」というアコーディオン見出し自体の見本を表示してはならない（ユーザーが「ヘルプの操作」なのか「見本」なのか混乱するため）。
- 見本にするのは**開いた先にある実操作ボタン・コントロールのみ**とする。

### 原則 4: 説明のない孤立アイコンの排除
- 見本を置く場合は、必ずその意味・用途を説明する文章とセットにする。
- 文字説明だけで直感的に理解できるものは、無理にアイコンを置かず文章のみに整理する。

### 原則 5: 領域境界の視認性（Border-2とコントラスト）
- ダークテーマのモーダルにおいて、カード枠線が 1px や低透明度（例: `gray-700/60`）だと背景と同化して「どこまでが1つの設定か」が分からなくなる。
- **カード外枠は `border-2 border-gray-600/80`**（開いた時は `border-gray-500/90`）を採用する。
- **太すぎの禁止**: 3px以上（border-4など）は野暮ったくなるため、2px を標準とする。
- **未定義CSSクラスのフォールバック防止**: Tailwind 等で未定義のカラー（例: `border-gray-750`）を指定すると、CSS仕様により `border-color` が `currentColor`（親の文字色＝白）にフォールバックして意図しない白線になる。必ず定義済みカラーを使う。

### 原則 6: デバイス・プラットフォーム最適化
- **表記の自動出し分け**: PC環境では「クリックで開閉」、スマホ環境では「タップで開閉」とレスポンシブに切り替える。
- **非対応機能の除外**: 特定のブラウザやOSで非対応の機能（例: Safariでの特定API非対応）がある場合、その環境のヘルプからは項目自体を自動非表示にする。

### 原則 7: 基本ルールの準拠（ライセンス・環境・注意事項）
- **動作確認環境 / 推奨環境**: どのブラウザ・OSで動作確認しているかを記載する。
- **注意事項**: 負荷の高い操作や保存時の注意点を明記する。
- **ライセンス情報の完全一致**:
  - アプリ本体のライセンス（GNU GPLv3, MIT等）を正確に記載する（`package.json` や `LICENSE` ファイルと完全一致させる）。
  - サードパーティ依存ライブラリ（直接依存・開発依存）の一覧、バージョン、ライセンス種別をアコーディオン等で網羅表記し、OSSコンプライアンスを徹底する。

### 原則 8: 自明な状態・位置の記述の全廃
- 「初期状態は閉じています」「開くと〜」「画面のいちばん上にある」「開いて設定から操作します」など、画面を見たら一目瞭然な状態・位置の解説はノイズになるため一切記述しない。
- 記述するのは「その機能がなぜ存在し、何ができるのか（目的）」と「具体的な操作方法・調整項目」に絞り込む。

### 原則 9: プラットフォーム・Flavor境界（非対応機能の自動除外）
- モバイルSafari（iOS/iPadOS）や特定ブラウザで未対応・非表示の機能がある場合、その環境のヘルプからは項目自体を自動フィルタリング（非表示）する。
- 非対応機能の操作説明を読ませて「ボタンが見当たらない」とユーザーを迷わせる事態を未然に防止する。

### 原則 10: 操作補助機能（ステッパー/スライダー）の明文化
- スライダー（粗調整: 例 0.5秒刻み）とステッパーボタン（微調整: 例 0.1秒刻み、長押し増減）のような、数値入力の操作補助機能がある場合は、その刻み幅の違いや長押し加速の仕様をヘルプで明記する。

### 原則 11: 多重モーダル（モーダル上のヘルプ）の安全設計
- 親モーダル（専用スタジオや詳細設定モーダル等）を開いたまま、さらに前面にヘルプモーダルをスタック表示（スライドアップ等）する場合の履歴制御を設ける。
- モバイルやブラウザの「戻る」操作（`popstate`）で親モーダルまで一緒に連動して閉じてしまわないよう、`history.pushState` やステート判定（例: `event.state?.__parentModal` が残っている場合は親を閉じない）による多重モーダル保護ガードを実装する。

### 原則 12: 前提条件に応じた動的案内（設定済み時のノイズ削減）
- APIキー登録や外部認証が前提となる機能では、未設定時には概要文（`description`）の直下に目立つ重要枠（黄色警告枠、外部取得リンク、生成ボタンの非活性化）を表示し、最優先で気づかせる。
- 一方、すでに設定を完了しているユーザーにとっては同じ警告が視覚的なノイズになるため、設定完了時は重要警告枠を自動で非表示（`null`）にする動的表示制御を徹底する。

### 原則 13: 実画面仕様と一致するリアル操作パネル見本
- アイコンやボタンを単に断片的に並べる（「アイコンがグチャッと固められている」）のではなく、実際の画面と寸分違わぬコントロールバー、ナビゲーション、打鍵ボタンをまとめたリアルな見本コンポーネント（例: タイミング打ちパネル、ミニヘッダー等）を提示する。
- ユーザーが一目で「実際の画面でこう動くんだ」と理解できるようにし、機能の魅力と直感的な使いやすさを伝える。

### 原則 14: 説明文内のインラインアイコン置換と安全な外部リンク
- 説明文中の「歯車アイコン」等のテキストを、正規表現分割（`/(Google AI Studio|歯車アイコン)/g`）によって実際のインラインアイコン（`<Settings />`）付きバッジへ動的置換する。
- 外部サービス（Google AI Studio等）へのリンクは `target="_blank" rel="noreferrer"` の外部リンクとして安全に描画し、クリックイベントの親伝播（`stopPropagation`）を防ぐ。

### 原則 15: 内部ロジック・配分ルール・一括設定メリットの構造化
- 時分割入力のように内部で文字数比例配分やアルファベット係数（例: 0.8）計算が行われている場合、その仕組みと「1行ごとに設定する手間が省ける」という圧倒的なメリットを、`facts`（事実・パラメータ）や `bullets` で明確に解説する。
- 単に「できます」と書くだけでなく、「なぜ便利なのか」「どう計算・動作しているのか」を構造化して伝える。

### 原則 16: セクション責務とカテゴリ整合性の徹底
- 他セクション（全体設定やプレビュー等）で管理されるべき項目（例: タイトル設定）が、関係のないセクション（例: キャプション）のヘルプに混入しないよう、セクション境界の責務を厳格に保つ。

### 原則 17: 認証・APIキーの安全性案内（不安排除の原則）
- 外部APIキーや認証情報をユーザーに登録させる際は、「登録したAPIキーはお使いのブラウザ内（ローカル）にのみ安全に保存され、外部サーバーには送信されません」と端的に安全性を明記する。
- **余計な技術的言及の排除**: 「直接通信します」「APIへ通信」といった記述は、ユーザーに「キーがどこかへ送信・流出するのではないか」という無用な不安を煽るため一切記述しない。ローカル隔離保存の事実のみを端的に伝える。

### 原則 18: 画面間・モーダル間の表記と視覚見本の一致（表記揺れ全廃）
- ヘルプモーダル内の説明と、業務モーダル（AIスタジオ等）内の警告ボックスや設定画面の案内表記を完全に一致させる。
- 「右上の設定」といった古い位置表現を放置せず、「トップ画面のタートルビデオ アプリ名の横の歯車アイコン」のように、現在の実画面レイアウトと完全に一致させ、必要に応じて実アイコン（`<Settings />`）付きバッジで案内する。

## 3. 推奨データスキーマ (TypeScript)

```typescript
export interface HelpBullet {
  text: string;
  visuals?: string[]; // 該当行にインライン表示する操作見本ID
}

export interface HelpItem {
  title: string;
  category: string;
  isSubAccordion?: boolean;
  description: string; // 導入要約 (140文字以内)
  bullets?: Array<string | HelpBullet>;
  facts?: Array<{ label: string; description: string }>;
  comparison?: {
    caption: string;
    rows: Array<{ label: string; description: string }>;
  };
  note?: string;
  visuals?: string[]; // 全体見本 (bulletsで未消化のもののみ末尾表示)
  accordions?: Array<{ // ライセンス一覧や詳細リスト用
    title: string;
    items: string[];
  }>;
}
```

## 4. 自動テストと品質保証のパターン

ヘルプ機能を追加した際は、以下の自動テスト（Unit Tests）を必ず整備する：

1. **文字数・文言バリデーション**:
   - 全項目の `description` が 140文字以内であること。
   - 「開くと」「初期状態は閉じて」等の状態記述が含まれていないこと。
   - 重要な数値や単位（「0.1秒単位」「実尺」等）が含まれていること。
2. **視覚見本（visuals）の完全整合性**:
   - 定義されたすべての visual ID が、UIコンポーネント側のレンダラーで正しく描画されること。
   - アコーディオン開閉ヘッダー枠の見本（`_accordion`）が混入していないこと。
3. **耐久性・Hooks安全性**:
   - 初期状態（全閉じ）から「すべて開く」で全カテゴリ・全子アコーディオンを一括展開しても、React Hooks のルール違反や再レンダリングループが発生しないこと。
